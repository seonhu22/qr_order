# Consumer 테이블 주문 가능 상태 요구사항

## Summary

테이블 비활성화를 방문 종료와 분리해 기존 주문 이용은 유지하고 신규 주문만 일시 차단한다. 기존 `table_info.use_yn`을 사용하며 DB 스키마는 변경하지 않는다.

---

## Problem Frame

QR 연결 후 생성된 Consumer 세션은 테이블이 나중에 비활성화돼도 세션에 저장된 테이블 정보로 계속 동작한다. 현재 신규 QR 연결은 비활성 테이블을 거부하지만, 이미 발급된 세션의 주문 생성은 테이블 상태를 다시 확인하지 않는다.

운영자는 테이블을 사용 중지하면서 추가 주문은 막아야 하지만, 이미 접수된 주문까지 종료하거나 고객의 주문내역 접근을 차단해서는 안 된다. 방문 생명주기와 주문 가능 상태를 같은 값으로 표현하면 결제 완료, 세션 만료, 일시적인 운영 차단의 의미가 섞인다.

---

## Actors

- A1. 소비자: QR 세션으로 메뉴를 보고 주문하며 같은 테이블의 주문내역을 확인한다.
- A2. 매장 직원: 테이블을 활성화/비활성화하고 기존 주문을 조리, 서빙, 결제 또는 개별 취소한다.

---

## Key Flows

- F1. 테이블 비활성화 중 기존 세션 이용
  - **Trigger:** 직원이 사용 중인 테이블을 비활성화한다.
  - **Actors:** A1, A2
  - **Steps:** 소비자는 기존 세션과 장바구니를 유지하고 메뉴 및 기존 주문을 조회한다. 신규 주문은 서버에서 거부된다. 직원은 이미 접수된 주문을 계속 처리한다.
  - **Outcome:** 신규 주문은 생기지 않으며 기존 방문과 주문 이력은 보존된다.
  - **Covered by:** R1, R2, R3, R6, R7
- F2. 테이블 재활성화
  - **Trigger:** 직원이 테이블을 다시 활성화한다.
  - **Actors:** A1, A2
  - **Steps:** 서버가 현재 테이블 상태를 다시 평가한다. 방문이 여전히 유효하면 주문 가능 상태가 복구된다.
  - **Outcome:** 활성 방문은 QR 재스캔 없이 다시 주문할 수 있고 종료/만료 방문은 복구되지 않는다.
  - **Covered by:** R4, R5, R8
- F3. 비활성 테이블 QR 신규 진입
  - **Trigger:** 소비자가 비활성 테이블의 QR을 새로 스캔한다.
  - **Actors:** A1
  - **Steps:** QR 연결이 비활성/무효 사유를 구분해 노출하지 않고 실패한다.
  - **Outcome:** 새 Consumer 세션이 발급되지 않는다.
  - **Covered by:** R9

---

## Requirements

**상태와 접근 범위**

- R1. 방문 상태와 주문 가능 여부를 별도 개념으로 관리한다.
- R2. 테이블 비활성화는 유효한 방문을 `CLOSED` 또는 `EXPIRED`로 변경하지 않는다.
- R3. 비활성화 중에도 메뉴, 공유 주문 목록 및 주문 상세 조회를 허용한다.
- R4. 테이블이 재활성화되고 방문이 아직 활성 상태라면 주문 가능 상태를 자동 복구한다.
- R5. 결제 완료 또는 만료된 방문은 테이블 재활성화로 복구하지 않는다.

**주문 차단**

- R6. 주문 생성은 저장을 확정하기 전에 현재 테이블 활성 상태를 서버에서 최종 확인한다.
- R7. 비활성 테이블의 주문 생성은 `409 Conflict`와 안정적인 사유 코드 `TABLE_INACTIVE`로 거부한다.
- R8. 프론트는 주문 가능 여부를 사전에 표시하고, 주문 도중 비활성화된 경합도 R7의 응답으로 처리한다.

**QR 진입**

- R9. 비활성 테이블의 신규 QR 연결은 현재와 동일한 일반 `404` 실패를 유지하며 비활성 여부를 외부에 구분해 노출하지 않는다.

**데이터와 사용자 경험**

- R10. 기존 `table_info.use_yn`을 상태의 원천으로 사용하고 테이블이나 컬럼을 추가하지 않는다.
- R11. 주문 차단 시 장바구니를 자동 삭제하지 않는다.
- R12. 이미 접수된 주문의 조리, 서빙, 결제 및 직원 개별 취소 흐름에는 영향을 주지 않는다.

---

## Acceptance Examples

- AE1. **Covers R1, R2, R3, R7, R11.** 활성 방문 중 테이블이 비활성화되면 기존 세션은 주문내역을 계속 조회하고 장바구니를 유지하지만 신규 주문은 `TABLE_INACTIVE`로 거부된다.
- AE2. **Covers R6, R8.** 주문 버튼을 누른 뒤 저장 확정 전에 테이블이 비활성화되면 주문은 생성되지 않고 프론트는 장바구니를 유지한 채 주문 차단 상태를 반영한다.
- AE3. **Covers R4, R5.** 비활성화됐던 테이블을 다시 활성화하면 활성 방문은 주문 가능 상태로 돌아오지만 결제 완료 또는 만료 방문은 돌아오지 않는다.
- AE4. **Covers R9.** 비활성 테이블 QR을 새로 스캔하면 무효 QR과 같은 일반 `404`가 반환되고 세션이 생성되지 않는다.
- AE5. **Covers R12.** 테이블 비활성화 전에 접수된 주문은 직원 화면에서 계속 조리, 서빙, 결제 또는 개별 취소할 수 있다.

---

## Success Criteria

- 테이블 비활성화 직후 기존 세션에서 신규 주문이 생성되지 않는다.
- 기존 고객은 비활성화 중에도 자신의 방문과 공유 주문내역을 확인할 수 있다.
- 테이블 재활성화 시 활성 방문만 주문 가능 상태를 회복한다.
- 프론트는 사전 차단과 주문 중 경합을 같은 비즈니스 사유로 안내한다.
- 전체 동작이 DB 스키마 변경 없이 구현되고 자동화 테스트로 검증된다.

---

## Scope Boundaries

- 서버 재시작/다중 서버를 넘는 영속 멱등성은 후속 작업으로 둔다.
- `requestNote` 저장을 위한 DB 컬럼 추가는 후속 작업으로 둔다.
- 복사된 QR의 외부 사용을 막는 선택형 PIN 인증은 TODO로 관리한다.
- 테이블 비활성화에 따른 기존 주문 자동 취소는 하지 않는다.
- Consumer SSE와 실시간 테이블 상태 푸시는 포함하지 않는다.
- DB 테이블, 컬럼, 인덱스 및 데이터 마이그레이션을 추가하지 않는다.

---

## Key Decisions

- 주문 권한 분리형을 채택한다: 방문 종료와 운영상 주문 차단은 서로 다른 상태다.
- `409 Conflict`를 사용한다: 인증 실패나 영구 종료가 아니라 현재 자원 상태와 주문 요청의 충돌이다.
- 비활성 신규 QR은 일반 `404`를 유지한다: QR과 테이블의 존재 여부를 추가로 노출하지 않는다.
- 재활성화는 현재 상태를 따른다: 별도 차단 이력을 저장하지 않고 활성 방문의 주문 권한을 복구한다.
- 서버 판정을 최종 기준으로 삼는다: 프론트 사전 차단만으로 주문 경합을 해결하지 않는다.
- 세션 계약은 `orderingAllowed: boolean`과 `orderingBlockedReason: 'TABLE_INACTIVE' | null`을 사용한다.

---

## Dependencies / Assumptions

- 매장 관리 기능이 기존 `table_info.use_yn`을 신뢰할 수 있게 갱신한다.
- 주문 조회와 직원 주문 처리 흐름은 테이블 활성 여부와 독립적으로 동작한다.
- API 응답 계약과 생성 클라이언트는 변경할 수 있다.

---

## Planning Decisions

- `ACTIVE`/활성은 `orderingAllowed: true`, 차단 사유 `null`이다.
- `ACTIVE`/비활성은 `orderingAllowed: false`, 차단 사유 `TABLE_INACTIVE`다.
- `CLOSED`/`EXPIRED`는 `orderingAllowed: false`, 차단 사유 `null`이다.
- 주문 잠금 순서는 테이블 → 방문 → 주문번호 범위로 통일한다.
