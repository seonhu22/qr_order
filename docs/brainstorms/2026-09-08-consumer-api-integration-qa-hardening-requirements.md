# Consumer API Integration / QA Hardening

## Summary

병합된 Consumer 세션/메뉴/주문 기능을 실제 백엔드 기준으로 검증하고, Client 앱의 주문 운영 기능까지 연결된 전체 흐름을 안정화한다. 모든 수정은 요구사항, 선택 이유, 테스트 결과와 커밋을 통해 추적할 수 있어야 한다.

---

## Problem Frame

Consumer MVP 기능과 Client 주문 관리 기능이 여러 브랜치에서 병합되었지만, 화면 표시만으로는 쿠키 기반 세션, API 계약, 상태 전이, 결제 처리와 실패 복구가 실제로 연결됐다고 판단할 수 없다. 수동 QA를 시작하기 전에 병합 누락과 실제 API 병목을 자동 검증하고, QA 담당자가 Client 앱을 이용해 운영 상태를 재현할 수 있어야 한다.

---

## Actors

- A1. Consumer 사용자: QR 세션으로 메뉴를 조회하고 주문을 생성/조회한다.
- A2. Client 직원: 접수 주문을 조회하고 조리/서빙/결제 상태를 변경한다.
- A3. 리뷰어/QA 담당자: 결정 근거와 테스트 증거를 따라 병합 결과와 전체 흐름을 검토한다.

---

## Key Flows

- F1. Consumer 주문 생성과 조회
  - **Trigger:** A1이 유효한 QR 세션에서 메뉴를 선택하고 주문한다.
  - **Actors:** A1
  - **Steps:** 세션 확인, 메뉴 조회, 장바구니 구성, 주문 생성, 주문 내역 확인 순서로 진행한다.
  - **Outcome:** 성공한 주문이 한 번 생성되고 Consumer 주문 내역에서 동일한 내용으로 조회된다. 실패 시 재시도 가능한 입력은 보존된다.
  - **Covered by:** R1, R2, R3, R7
- F2. Client 주문 운영과 Consumer 반영
  - **Trigger:** A2가 Consumer가 생성한 주문을 Client 주문 현황에서 연다.
  - **Actors:** A1, A2
  - **Steps:** 주문 조회, 메뉴/옵션/수량/금액 확인, 주문 상태 변경, 결제 완료 처리, Consumer 조회 결과 확인 순서로 진행한다.
  - **Outcome:** 양쪽 앱이 동일 주문과 서버 상태를 일관되게 표시한다. 실패한 변경은 성공처럼 보이지 않는다.
  - **Covered by:** R4, R5, R6
- F3. 장애와 접근 불가 복구
  - **Trigger:** 세션 또는 주문 요청 중 네트워크 단절, 시간초과, 비활성 테이블이나 종료된 세션을 만난다.
  - **Actors:** A1, A3
  - **Steps:** 오류를 식별하고 사용자에게 상태를 표시한 뒤, 복구 가능한 경우 입력을 보존하여 다시 시도한다.
  - **Outcome:** 복구 가능 오류와 복구 불가 세션 상태가 구분되고 장바구니 처리 정책이 지켜진다.
  - **Covered by:** R3, R7, R8

---

## Requirements

**병합 및 실제 API 연결**

- R1. 현재 브랜치에 병합된 Consumer 세션/메뉴/주문 기능의 누락, 충돌 잔재와 계약 불일치를 검사한다.
- R2. 자동 및 수동 QA의 기준 환경은 실제 백엔드를 사용하는 `dev:real`로 한다.
- R3. Consumer의 세션 조회, 메뉴 목록/검색/상세, 주문 생성/목록/상세가 실제 요청과 응답을 통해 연결되어야 한다.

**Client 기반 운영 검증**

- R4. Client 주문 현황은 Consumer 주문의 메뉴, 옵션, 수량과 금액을 조회할 수 있어야 한다.
- R5. Client에서 지원하는 주문 상태 변경이 실제 API에 반영되고 이후 조회에서도 유지되어야 한다.
- R6. Client의 결제 완료 처리가 실제 API에 반영되고 양쪽 앱에서 일관되게 확인되어야 한다.

**장애/재시도 정책**

- R7. 주문 실패가 확정되지 않은 동안 장바구니와 동일 요청 식별자를 보존하고, 성공이 확인된 뒤에만 비운다.
- R8. 종료/만료 세션에서는 이전 방문 장바구니를 제거하고, 테이블 비활성이나 일시적 네트워크 오류에서는 재시도할 장바구니를 유지한다.
- R9. MSW는 실제 서버에서 안전하고 결정적으로 만들기 어려운 네트워크 단절/시간초과 등의 보조 시나리오에만 사용한다.

**증거와 추적성**

- R10. 완료 판단은 관련 자동 테스트, 타입 검사, 린트, 빌드, 적용 가능한 백엔드 테스트와 수동 QA 절차의 결과에 근거한다.
- R11. 발견된 결함마다 원인, 수정 선택 이유, 영향 범위, 검증 방법과 관련 커밋을 추적할 수 있게 기록한다.
- R12. 원격 저장소에는 push하지 않으며, 로컬 커밋까지만 허용한다.
- R13. 2026-09-08 안에 이 문서의 범위에 대한 검사, 필요한 수정, 검증과 보고를 완료한다.

## Acceptance Examples

- AE1. **Covers R2, R3.** 유효한 실제 QR 세션에서 주문하면 서버가 성공 응답을 반환하고, 생성된 주문이 Consumer 주문 목록/상세와 Client 주문 현황에 같은 항목으로 나타난다.
- AE2. **Covers R5, R6.** Client에서 주문 상태를 변경하고 결제 완료 처리하면 재조회 후에도 서버 상태가 유지되며 Consumer가 조회하는 주문과 모순되지 않는다.
- AE3. **Covers R7.** 주문 응답을 받지 못한 뒤 다시 시도할 때 같은 요청 식별자가 전송되며, 주문 성공이 확인된 뒤 장바구니와 식별자가 제거된다.
- AE4. **Covers R8.** 종료/만료 세션으로 판정되면 장바구니가 제거되지만, 테이블 비활성 또는 네트워크 오류에서는 장바구니가 유지된다.
- AE5. **Covers R9.** 실제 API 계약과 상태 전이는 `dev:real`에서 확인하고, 네트워크 단절/시간초과 재현만 MSW 시나리오로 보완한다.
- AE6. **Covers R10, R11.** 최종 보고서에서 각 요구사항의 코드/API, 테스트 결과, 수동 확인 항목과 커밋을 역추적할 수 있다.

## Success Criteria

- Consumer 주문이 실제 백엔드를 거쳐 Client 운영 화면에 나타나고 상태 변경/결제 결과가 재조회에도 유지된다.
- 주요 성공/실패/복구 경로가 자동 테스트 또는 재현 가능한 수동 QA 절차로 증명된다.
- 리뷰어가 보고서만으로 변경 이유, 남은 한계와 검증 증거를 확인할 수 있다.
- 계획 단계에서 사용자 동작, 완료 조건 또는 범위 경계를 새로 발명할 필요가 없다.

---

## Scope Boundaries

- DB 테이블, 컬럼과 마이그레이션 변경
- 서버 영속 멱등성 구현과 그에 필요한 DB 저장 구조
- `requestNote` 저장 구조
- Consumer 전용 SSE와 참여 인원 기능
- 직원 호출과 서버 장바구니
- QR 외부 사용 차단용 PIN
- 현재 통합 검증과 직접 관계없는 구조 개선
- 원격 브랜치 push

## Key Decisions

- 실제 백엔드 우선: MSW만으로는 세션 쿠키, 실제 DTO/쿼리/트랜잭션과 상태 코드를 검증할 수 없으므로 `dev:real`을 기준으로 삼는다.
- Client 실제 기능 우선: 테스트 전용 제어 대신 현재 운영 UI/API로 상태와 결제를 만들어 전체 시스템 연결을 검증한다.
- 기존 구현 우선: 병합된 코드와 프로젝트의 기존 패턴을 먼저 활용해 중복 구현과 회귀 가능성을 낮춘다.
- 제한적 QA 보조: 실제 환경에서 재현 비용이 큰 전송 장애만 MSW로 보완해 실제 연동 검증과 오류 UI 검증의 역할을 분리한다.
- DB 없는 멱등성 한계 명시: 현재 프로젝트 권한과 일정상 프론트 재시도 식별자 안정성까지만 검증하고 서버 영속 보장은 후속 작업으로 남긴다.
- 증거 기반 완료: 화면 관찰이 아닌 재현 가능한 테스트 결과와 요청/응답을 완료 판단의 근거로 사용한다.

---

## Dependencies / Assumptions

- 실제 백엔드와 개발용 데이터베이스가 로컬에서 실행 가능하고 유효한 QR 세션을 준비할 수 있다.
- Client 계정에 주문 조회, 상태 변경과 결제 처리 권한이 있다.
- 필요한 백엔드 수정은 API/서비스/매핑/테스트 범위에서 허용되지만 DB 스키마 변경은 허용되지 않는다.
- 실시간 갱신 기능은 이번 범위가 아니므로 상태 반영은 명시적 재조회로 검증할 수 있다.
