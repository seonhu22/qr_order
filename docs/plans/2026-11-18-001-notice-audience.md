# 공지 대상별 알림 구현

## 승인 범위와 근거

- 사용자 승인(2026-11-18): 대상 컬럼 추가 SQL 준비/실제 DB 적용은 사용자가 수행한다.
- 수신 대상은 all/manager/staff이며 기존 공지는 all로 유지한다.
- 기존 공지 API에서 서버가 역할별로 필터링하고 현재 60초 조회 방식을 유지한다.
- 조사 근거: [연결 누락](../qa/2026-11-18-notice-audience-discovery.md).
- 기존 정책: [관리자 알림](../../frontend/docs/page/manager-notifications.md)의 로컬 읽음과 직원호출 동작을 유지한다.

## 구현 단위와 이유

1. SQL/저장 계약: brd_notice.target의 허용값/기본값/설명을 정의하고 기본 ROLLBACK의 사전 실행 SQL과 복구 조건을 제공한다. 서버 재시작으로 기존 데이터가 사라지지 않아야 하므로 UI 상태만으로 대상을 저장하지 않는다.
2. Admin 저장/조회: DTO/Mapper/직렬화에 target을 연결한다. 생성 생략은 all, 수정 생략은 기존 값 유지, 알 수 없는 값은 저장 전에 거부한다. 수정 시 현재 저장값 보존은 트랜잭션과 SQL에서 보장한다.
3. Client 조회: 세션의 현재 사용자 역할01/02에서 대상 역할을 도출한다. 요청자가 넘긴 역할은 믿지 않는다. 기존 시스템 공지의 전역 공개 범위는 바꾸지 않는다.
4. Client 알림: 관리자/스태프가 대상 공지를 조회한다. 문의 답변은 관리자만 조회하고 직원호출 확인 동작은 유지한다. 계정/매장 외 역할도 query key에 포함해 역할 전환에서 캐시가 섞이지 않게 한다.
5. OpenAPI/생성 타입: 실제 격리 서버의 DTO 스키마와 기존 명세를 대조한 뒤 생성 도구를 실행한다. 생성 파일을 수동 수정하지 않는다.
6. 검증/보고: 실제 임시 PostgreSQL 저장과 필터/정확한 FormData/역할 전환/직원호출 회귀를 확인한다. 공유 DB 적용과 dev:real 수동 QA는 별도 미완료 게이트로 기록한다.

## 배포 경계

- 사용자가 SQL dry-run 결과 확인 후 적용한다. 이 작업에서 공유 DB에 접속해 DDL을 실행하지 않는다.
- DB 컬럼 적용 뒤 백엔드, 그 뒤 프론트를 반영한다.
- 사용자 역할이나 대상 값을 기존 컬럼에 임의로 인코딩하는 우회는 사용하지 않는다.
- 신규 SSE/기기 간 읽음 동기화/별도 알림 테이블은 범위에 포함하지 않는다.

## 검증할 영향 체인

DB 제약 → Admin 저장 Mapper → DTO → OpenAPI/생성 타입 → Admin draft와 조회 매퍼 → multipart 직렬화 → Client 서버 역할 필터 → 알림 훅/헤더 → 통합 테스트 → 실제 DB 적용과 수동 QA.

각 경계의 실제 결과는 완료 보고서에 기록한다. 단일 계층 테스트 통과만으로 통합 완료로 표시하지 않는다.
