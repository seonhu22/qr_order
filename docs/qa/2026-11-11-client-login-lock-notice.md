# Client 로그인 제한 안내 검증

## 요구와 확인 근거

- 사용자 결정: 다섯 번째 실패부터 잠금/제한 안내를 표시한다.
- 실제 `LoginController`는 실패 시 HTTP 401과 `data=e.getData()`를 응답한다.
- 기존 Admin은 숫자/숫자 문자열/snake-case와 camel-case 객체/잠금 메시지를 처리했지만 Client는 일반 인라인 오류만 표시했다.
- Client 훅 테스트에서 횟수 5의 401/200 응답과 잠금 메시지 3개가 먼저 실패했다. 이후 최소 실패 처리 분기만 수정했다.

## 커밋을 읽는 순서

1. `91b23566`: 기존 실패 응답 해석을 공용 함수와 계약 테스트로 분리.
2. `ff3c4e22`: Admin의 중복 함수만 공용 import로 교체. 기존 화면/조건 유지.
3. `5bea7602`: Client 실패 처리에 안내 모달/비밀번호 초기화 연결.
4. `8e285518`: 실제 Chromium에서 서버 횟수 1~4/5 응답의 화면 차이 검증.
5. `e0d87968`: `/auth/me`가 이미 사용자 data를 제공한다는 사실에 맞춰 오래된 TODO 주석 정정.
6. `e8aeb3bf`: 안내/서버 잠금 경계와 현재 인증 캐시 문서 정정.

한 번에 읽지 않으려면 `git show 91b23566`부터 하나씩 확인한다. 실행 변경과 단순 문서 정정은 커밋으로 구분했다.

## 변경 이유

- 공용 helper는 Admin과 Client의 응답 해석이 다시 달라지는 것을 막기 위해 추출했다.
- 기존 결과 모달을 재사용해 새로운 화면/연락처/해제 정책을 만들지 않았다.
- 일반 실패와 서버 오류는 기존 인라인 상태를 유지한다. 잠금 신호일 때만 비밀번호를 비우고 중복 인라인 오류를 제거한다.
- 프론트 카운터를 만들지 않았다. 서버가 잘못 응답하는 값을 브라우저마다 따로 보정하면 새로고침/기기/동시 요청에서 계약이 달라진다.
- `AuthProvider`의 실제 기준은 `auth.me`이고 과거 문서의 `auth/profile` 경로는 현재 코드에 없어 문서를 정정했다. 인증 실행 로직은 이 정정에서 바꾸지 않았다.

## 확인한 결과

- helper 계약 14개 통과.
- Client 훅의 실제 httpClient/생성 mutation/MSW/React Query/모달 상태 통합 8개 통과.
- 기존 AppRoutes 회귀를 포함한 2개 파일/24개 테스트 통과.
- Client 브라우저 1개 통과(10.5초): 5회 응답의 모달은 하나이며, 확인 후 비밀번호는 비우고 아이디/경로는 유지.
- 읽기전용 검토: 수정 요구 결함 없음. `/api/auth/`의 401은 기존 전역 인증 만료 모달 제외 정책으로 중복 표시되지 않는다.
- 최종 `npm run verify` 종료 코드 0. 스크립트 6개/153파일의 단위 테스트 674개/브라우저 14개/일반과 E2E 타입/lint/build 모두 통과했다. 앞선 메뉴 권한 변경도 포함한다.
- 로컬 증거 폴더: `frontend/src/test/test-result/verify-2026-11-11-050528-975-7684/`. 로그/JSON은 Git에 올리지 않는다.

## 완료하지 않은 서버 범위

- 현재 서버는 증가 전 실패 횟수와 `> 5` 사전 검사이므로 실제 다섯 번째 실패 차단은 완료되지 않았다.
- 프론트 안내를 서버 인가/잠금 정책의 대체로 보고하지 않는다.
- 백엔드 수정 허가, 전용 QA 계정과 복구 방법을 확보한 뒤 실제 카운트/잠금 유지/정상 비밀번호 거부를 검증해야 한다.
- DB 스키마/백엔드 소스/API DTO/OpenAPI/생성 타입은 변경하지 않았다. 기존 응답을 사용하는 프론트 매핑/transport 통합만 검증했다.
- push/원격 CI/공유 DB 변경은 수행하지 않았다.
