## 관찰 결과

- 사전 서버 연결 검사 통과. 이전 실행의 502는 이번 실행에서 재현되지 않았다.
- A매장 관리자: 로그인/실제 userId·매장·역할·initPwdRequired 검사/목록 API 200/사용자 관리 화면 표시 통과.
- A매장 스태프: 로그인/실제 userId·매장·역할·initPwdRequired 검사 통과.
- 실패 경계: 스태프 세션의 `GET /api/client/store_manage/user_manage/search`.
- 기대 403 / 실제 200. 승인 정책상 사용자 관리는 관리자 전용이므로 기대값을 변경하지 않는다.
- 스태프 화면 차단 검증/B매장 검증은 실패 지점 뒤라 실행되지 않았다.
- 주문/결제/비밀번호 변경/DB 초기화는 실행하지 않았다. 로그인과 화면 접근 이력은 서버에 남을 수 있다.
- 계정 비밀번호/쿠키/목록 본문은 이 문서에 저장하지 않는다.

## 원인 범위와 다음 단계

- [최신 WebConfig](../../qrorder/src/main/java/htms/QROrder/config/WebConfig.java)는 사용자 관리 경로에 ClientMenuRoleInterceptor를 적용한다.
- [최신 ClientUserService](../../qrorder/src/main/java/htms/QROrder/client/service/ClientUserService.java)는 목록 조회에도 requireManager를 적용한다.
- 원본 체크아웃 `7b088dd3`에는 위 사용자 관리 역할 차단이 없다. 현재 서버가 이전 코드를 실행하는 경우 관찰 결과와 일치한다.
- 실행 서버의 커밋과 설정을 직접 확인하지 못했으므로 원인을 이전 버전 실행으로 단정하지 않는다.
- 서버 실행자가 최신 권한 코드 반영/재시작 여부를 확인한 뒤 같은 명령을 재실행한다.
- 최신 코드인데도 200이면 실행 중 인가 경로와 세션 역할 매핑을 조사한다. 테스트 완화를 통한 통과 처리는 하지 않는다.

## 별도 보안 후속

- 기존 스태프 `init_yn=N`/최초 변경 화면 미표시는 사용자 확인 사항이다.
- 신규 생성은 최신 코드상 Y이므로 기존 데이터/서버 버전/변경 이력을 대조한 후 원인을 확정한다.
- 변경 강제 기능을 이번 QA에서 임의로 켜거나 기존 비밀번호를 초기화하지 않는다.
