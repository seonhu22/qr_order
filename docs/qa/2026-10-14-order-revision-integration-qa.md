## 자동 검증 결과

2026-10-14 기준 아래 검증을 통과했다.

- 프론트 주문 수정 테스트: 3개 파일/13개 테스트
- 프론트 TypeScript 타입 검사
- 백엔드 `OrderRevision*` 테스트: 7개 클래스/50개 테스트

자동 테스트 통과는 실제 PostgreSQL/브라우저 통합 QA를 대신하지 않는다.

## 공통 준비

1. 백엔드와 프론트엔드를 같은 커밋 기준으로 실행한다.
2. Client 앱에 로그인하고 주문현황을 연다.
3. Chrome 개발자 도구의 Network에서 `Preserve log`를 켠다.
4. 테스트마다 새로운 주문과 새로운 `clientRequestId`를 사용한다.
5. 실패 응답 뒤에는 목록/DB가 일부만 변경되지 않았는지 확인한다.

## QA-4 전체 메뉴 제거

1. `RECEIVED` 주문의 모든 메뉴를 취소하고 수정 저장한다.
2. 저장 요청이 `200`인지 확인한다.
3. 주문현황에서 원래 주문이 사라지고 취소내역에 나타나는지 확인한다.
4. 취소사유가 `주문 수정`으로 표시되는지 확인한다.
5. DB에서 상태 `99!`, `cancel_yn=Y`, `cancel_type=ORDER_REVISION`인지 확인한다.

통과 기준: 유효 메뉴가 0개인 원본 주문만 자동취소되고 다른 주문은 변하지 않는다.

실행 결과: 전체 메뉴 제거 후 자동취소/취소내역/상태가 기대값과 일치했다.

## QA-5 상태/테이블 비활성 경계

### 주문 상태

- `RECEIVED`/`COOKING`: 수정 버튼과 저장을 허용한다.
- `SERVED`/취소/결제완료: UI에서 수정을 제공하지 않는다.
- 상태가 화면을 연 뒤 변경된 경우 저장 요청은 `409`이며 변경을 남기지 않는다.

### 비활성 테이블

1. 테이블을 비활성화한다.
2. 제거만 저장하면 허용되는지 확인한다.
3. 메뉴 추가 또는 제거와 추가를 함께 저장하면 `409`/`TABLE_INACTIVE`인지 확인한다.
4. 거절된 요청의 제거 이력과 신규 주문이 DB에 없는지 확인한다.

통과 기준: 새 메뉴가 생기는 수정만 차단하고 실패 요청은 원자적으로 롤백된다.

실행 결과: 접수/조리중 허용, 서빙완료 차단, 비활성 테이블의 제거 허용과 추가 차단이 모두 기대값과 일치했다.

## QA-6 멱등성

1. 성공한 수정 POST를 Network에서 선택해 요청 본문과 `clientRequestId`를 보관한다.
2. 같은 ID/같은 본문으로 `Replay XHR` 또는 `Resend`한다.
3. 최초 응답과 같은 `revisionId`/결과가 반환되고 신규 주문/제거 이력이 늘지 않는지 확인한다.
4. 같은 ID에서 메뉴나 수량만 바꿔 다시 전송한다.
5. `409`/`ORDER_REVISION_PAYLOAD_MISMATCH`이고 DB가 변하지 않는지 확인한다.

통과 기준: 같은 의도는 한 번만 저장되고, 같은 키의 다른 의도는 거절된다.

실행 결과: 동일 payload replay는 같은 성공 결과를 반환했고, 같은 ID의 변경 payload는 `409`로 거절됐다. 중복 저장은 없었다.

## QA-7 네트워크 실패 후 재시도

1. 수정 모달에서 제거/추가 내용을 만든다.
2. Network를 Offline으로 바꾸고 저장한다.
3. 처리 중 표시가 끝난 뒤 입력 내용과 `clientRequestId`가 유지되는지 확인한다.
4. Online으로 복구하고 다시 저장한다.
5. 성공 뒤 모달/draft/`clientRequestId`가 초기화되고 변경이 한 번만 반영되는지 확인한다.

통과 기준: 실패 중 사용자의 입력을 잃지 않고 재시도가 중복 저장을 만들지 않는다.

### 실행 결과

- Offline에서 확인 버튼이 스피너/오류 없이 흰색 비활성 상태로 멈췄다.
- Network 요청과 콘솔 오류가 발생하지 않았다.
- Online 복구 뒤 요청은 `200`으로 한 번만 저장됐다.
- 다음 수정 작업에서는 새로운 `clientRequestId`가 사용됐다.
- 데이터 안전성은 통과했지만, 오프라인 상태 안내와 명시적 재시도 UX는 실패했다.

원인 후보: React Query의 기본 mutation 동작이 오프라인 요청을 실패시키지 않고 일시 정지한 뒤 연결 복구 시 자동 재개한다. 후속 작업은 [프론트엔드 TODO](../../frontend/docs/todo.md#주문-수정-오프라인에서-저장-버튼이-무응답처럼-표시됨)에 기록한다.

## QA-8 조회/금액 정합성

선행 조건 완료: Client 옵션 관리의 빈 행 렌더링과 `soldOutYn` 저장 계약을 수정했고, 사용자가 올바른 워크트리의 `dev:real`에서 저장 오류 해소를 확인했다. [계약 누락 QA 보고서](./2026-10-22-menu-option-sold-out-contract-gap-report.md)의 재개 조건을 기준으로 카탈로그 반영을 확인하면서 아래 비교를 진행한다.

수정한 주문을 다음 화면/API에서 비교한다.

- Client 주문현황/취소내역
- Consumer 주문 목록/상세
- 결제 영수증/결제 완료
- 미결제 내역
- 주문이력/정산

통과 기준: 제거 메뉴와 그 옵션은 모든 합계에서 제외되고, 살아 있는 메뉴/옵션과 신규 주문은 한 번만 포함된다. 원본 `payment_yn`은 주문 수정으로 바뀌지 않는다.

## QA-10 동시 요청

1. 일반 창과 시크릿 창에서 같은 주문을 연다.
2. 서로 다른 수정 내용을 준비한다.
3. 가능한 한 동시에 저장한다.
4. 한 요청만 성공하고 다른 요청은 `409`인지 확인한다.
5. 성공한 요청만 DB와 화면에 온전히 반영됐는지 확인한다.

통과 기준: 두 수정이 섞이거나 일부만 저장되지 않는다.
