# 메뉴 저장 `sold_out_yn` 계약 누락 보고서

## 근거

- 수동 QA에서 메뉴 신규 저장 시 `store_menu_detail.sold_out_yn NOT NULL` 위반 `500`이 발생했다.
- DB에는 필수 컬럼이 있었지만 `MenuDetailItem`, MyBatis 조회/저장 SQL, 생성 API 타입과 프론트 요청 mapper에 값이 없었다.

## 수정 이유와 범위

단순히 INSERT에 `N`을 고정하면 기존 품절 메뉴를 수정할 때 `Y`가 사라질 수 있다. 따라서 아래 계약 전체를 연결했다.

```text
DB NOT NULL
→ MyBatis 조회/INSERT/UPDATE
→ 백엔드 DTO
→ OpenAPI와 생성 타입
→ 프론트 행 모델
→ 응답 mapper
→ 요청 mapper
→ FormData 직렬화
→ 계약 테스트
```

- 신규 메뉴: 숨은 기본값을 `N`으로 전송하며 서버도 누락 시 `N`으로 보정한다.
- 기존 메뉴: 조회한 `Y/N`을 행 모델에 보존하고 수정 요청에도 그대로 전송한다. 구형 요청에서 값이 빠져도 서버가 기존 값을 보존한다.
- 서버는 최종 값이 `Y/N`이 아니면 저장 전에 거부한다.

## 검증

- 백엔드 전체 테스트: 통과
- 프론트 메뉴 계약 테스트: 4건 통과
- 프론트 타입 검사, lint, production build: 통과
- 프론트 전체 테스트: 590건 중 589건 통과. 기존 주문 멱등성 테스트 1건이 5초 제한으로 실패했으나 해당 파일만 재실행하면 17건 모두 통과했다.

## 수동 QA

`dev:real` 재시작 후 메뉴 관리에서 다음을 확인한다.

1. 신규 메뉴 행 추가와 저장이 `200`이고 DB `sold_out_yn = 'N'`이다.
2. 기존 `sold_out_yn = 'Y'` 메뉴의 가격만 수정해도 DB 값이 `Y`로 유지된다.
