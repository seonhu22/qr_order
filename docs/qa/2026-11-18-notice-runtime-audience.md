# 대상별 공지 / 실행 서버 버전 확인

- 사용자: 스태프도 모든 공지를 본다고 보고했다.
- 실제 API 검사에서 관리자01/스태프02의 인증 역할은 정상이나 공지 목록8건의 ID가 동일했다.
- 실행 서버 localhost:8080/v3/api-docs의 NoticeRequest/NoticeResponse는 존재하지만 target 속성이 없었다.
- 최신 소스의 DTO/ClientNoticeMapper에는 target과 역할 필터가 있다. 원본 build/resources의 이전 Mapper에는 필터가 없었다.
- 따라서 우선 해결 경계는 캐시나 역할 추측이 아니라 최신 백엔드 실행 반영이다. 프론트에서 공지 제목을 보고 대상을 추측해 숨기지 않는다.

## 조치와 다음 확인

1. 원본 qrorder의 최신 소스를 gradlew classes로 컴파일한다. 공유 DB 쓰기나 서버 강제 종료는 하지 않는다.
2. 실행 중인 백엔드를 종료하고 최신 원본/워크트리 코드로 재시작한다. OpenAPI의 두 Notice 스키마에 target이 있는지 확인한다.
3. Admin 공지를 다시 조회한다. 구버전 서버에서 등록했다면 대상 값이 기본 all로 남았을 수 있다. 제목으로 데이터를 자동 보정하지 않는다.
4. 테스트 공지의 실제 대상을 관리자/스태프로 다시 선택해 저장하고, 새로고침 후 유지되는지 확인한다.
5. 관리자와 스태프 각각 API 응답과 알림을 비교한다. 전체+본인 역할 공지만 있어야 한다.

새 필터 코드는 이미 구현/자동 검증돼 있다. 이번 조사에서는 중복 제품 코드 변경 없이 실행 버전의 누락을 확인했다. 실제 수정 후 API 재검증은 재시작/대상 재저장 이후 수행한다.

관련 절차: [대상별 알림 적용과 QA](./2026-11-18-notice-audience-integration.md).

## 수동 QA 결과

사용자는 최신 서버에서 Admin과 Client를 일반 창과 시크릿 창으로 분리한 뒤 공지 수정과 조회가 정상 동작한다고 확인했다. 같은 브라우저 세션에서 Admin 로그인 후 Client 조회가 403이었던 사례도 창 분리로 해소됐다. 전체 수동 QA 완료는 사용자 확인을 근거로 기록한다.
