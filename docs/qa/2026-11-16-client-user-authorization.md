# 사용자 관리 권한 보완 / 검증 보고서

## 결과와 근거

- [승인 플랜](../plans/2026-11-16-001-fix-client-user-authorization-plan.md)의 A안으로 구현했다. 기존 API/Service/Mapper를 유지하고 시스템 관리자 승격만 분리했다.
- 근거: 기존 등록 SQL이 요청 매장/역할을 저장하고, 수정/삭제 SQL에는 대상 매장/역할 조건이 없었다.
- 일반 등록은 서버 매장/02로 고정하고, 수정은 이름만 허용한다. 일괄 삭제는 미허용 대상 혼입 시 전체 거부/롤백한다.
- 현재 DB 권한을 요청당 한 번 확인하고 후속 계층이 재사용한다. 삭제/매장 변경은 세션을 거부하고 로그인용 잠금 조회는 재사용하지 않는다.
- `POST /api/system/client-users/{sysId}/promote`는 시스템 관리자만 일반 매장02→01을 수행한다. 이미01인 재요청은 수정 시각도 바꾸지 않는다.
- DB 스키마/의존성/공통코드 원본/CSRF 정책은 변경하지 않았다. 공유 DB 접근/원격 push/병합도 하지 않았다.

## 변경 이유 / 선택한 경계

- 세션은 식별용, 현재 권한은 DB 기준이다. 같은 요청의 반복 조회는 피하고 요청 간 오래된 역할 캐시는 두지 않았다.
- Service의 정책 검사와 SQL의 대상 조건을 함께 사용한다. 프론트나 단일 URL 검사만으로 보안을 보장하지 않는다.
- 일반 저장에서 역할을 변경하지 않아 Client 관리자가 다른 관리자를 강등한 뒤 초기화하는 우회도 열지 않는다.
- 삭제/승격은 정렬된 대상 잠금과 조건부 갱신을 사용한다. 새 권한 시스템/운영 인프라 없이 현재 트랜잭션 구조에 맞췄다.
- 프론트는 같은 매장 스태프만 조작하며 확인 시 계정/매장/권한을 다시 검사한다. 등록/수정 본문에서도 허용 필드만 보낸다.

## 실행 중 발견한 문제와 수정

- 독립 1차 검토 **8.8/10**: 관리자 A→B 인증 전환 때 검색어만 사용한 queryKey로 A 목록 캐시가 노출될 수 있었다. 변경 요청은 서버가 차단해도 목록 노출은 별도 문제였다.
- 실제 AuthProvider/HTTP/같은 QueryClient에서 실패를 재현했다. 계정/매장별 키 분리와 현재 매장 행 필터를 추가하고 식별자 누락 시 조회를 막았다.
- 독립 2차 검토 **9.3/10**: 남은 P1/P2 조치 없음. 보안3.0/3 / 계약2.4/2.5 / 회귀2.2/2.5 / 유지보수1.7/2. 점수는 코드/자동검증 기준이며 운영 준비도 점수가 아니다.
- 첫 전체 백엔드 검사에서 기존 SQL 문자열 추출 테스트1개가 실패했다. 실제 MyBatis statement를 검사하도록 변경해 로그인 잠금 유지/일반 인가 무잠금을 확인했다. 제품 검증 조건을 제거하지 않았다.
- 최초 새 브라우저 검사1개는 콤보박스의 이름을 표시값인 “스태프”로 찾아 실패했다. 실제 접근성 이름 “권한”으로 찾고 비활성/표시값을 각각 검증해 통과했다.

## 실제 PostgreSQL 검증 범위

- 설치된 PostgreSQL16 바이너리로 작업 폴더 `qrorder/build/tmp/user-auth-postgres-*`에 고유 임시 클러스터를 만들었다. 기존 DB 설정/공유 DB/시스템 서비스는 사용하지 않았다.
- 실제 Mapper XML과 Spring 트랜잭션 프록시를 연결했다. Audit만 mock이며 암호화/영속 SQL/트랜잭션은 실제 실행했다.
- 정상02 등록/이름 수정/매장과 역할 보존, 타 매장 혼합 삭제 거부를 확인했다.
- 테스트 전용 trigger로 일부 UPDATE 뒤 건수 불일치를 유도하고 전체 쓰기가 롤백됨을 확인했다.
- 승격 중복 시각 불변/승격 우선/삭제 우선의 두 연결 경합을 검증했다. `pg_stat_activity`에서 실제 Lock 대기를 확인했다.
- 테스트 종료 시 생성한 클러스터만 중지한다. 프로세스 종료는 로그/`postmaster.pid` 부재/`pg_ctl status`로 확인했고 임시 파일은 build 폴더에 남는다.
- 독립 최소 스키마 검증이다. 운영 DDL 전체/실제 계정/성능 검증은 아니다. 바이너리 없는 환경은 명시적으로 미실행 처리하므로 CI 성공만으로 PostgreSQL 통과를 추정하지 않는다.

## 계약 영향 경계

- DB 스키마/기존 제약: 변경 없음. 실제 운영 스키마 호환성은 미검증.
- Mapper/Service 트랜잭션: 실제 PostgreSQL SQL/롤백/두 연결 경합 검증.
- Controller/DTO/HTTP: 기존 요청 형식 유지/정책 강화. 승격은 새 HTTP API이며 Service/MockMvc 인가 테스트를 연결했다.
- OpenAPI/생성 타입: DB 없이 격리 실행한 실제 springdoc HTTP에서 승격 명세를 추출했다. 기존 CommonResponse 일치를 확인하고 새 경로만 병합한 뒤 생성 명령을 실행했다. 운영 서버 전체 명세 재조회는 미실행.
- 프론트 모델/응답/요청/직렬화: 실제 HTTP 클라이언트/MSW 본문 및 계정 전환 테스트로 확인했다.
- 브라우저: 실제 Chromium/모의 API로 검증. `dev:real`은 대기.
