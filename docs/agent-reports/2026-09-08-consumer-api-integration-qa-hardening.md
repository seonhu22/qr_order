# Consumer API 통합 / QA 보강 결과

## 결론

병합된 Consumer 세션/메뉴/주문 생성/목록/상세 연결을 특성 테스트로 확인했고, 주문 완료 화면의 주문번호 전달 누락을 수정했다. Client 주문현황은 실제 API를 사용하며, 상태 변경과 결제 API의 매장/상태/방문 범위를 서버에서 검증하도록 보강했다.

자동 검증과 새 백엔드 프로세스의 OpenAPI 확인은 통과했다. 실제 DB 데이터와 로그인 세션이 필요한 `dev:real` 브라우저 시나리오는 백엔드를 현재 브랜치로 재시작한 뒤 수동 실행해야 하므로 완료로 표시하지 않는다.

## 선택과 이유

| 선택 | 이유 | 배제한 방식 |
|---|---|---|
| 병합 흐름을 먼저 특성 테스트로 고정 | 이미 구현된 기능을 다시 만들지 않고 병합 누락만 식별하기 위해 | 화면 표시만 보고 연결 완료로 판단 |
| 장바구니를 방문 식별자 3개로 격리 | 현재 프로젝트의 세션 모델로 다른 방문/매장/테이블 노출을 막을 수 있기 때문에 | DB 스키마가 필요한 서버 장바구니 |
| 실패 재시도에 같은 `clientRequestId` 유지 | 응답 유실 뒤 재시도에서도 동일 요청임을 표현하기 위해 | 재시도마다 새 ID 생성 |
| 상태 전이를 서버에서 매장/현재 상태로 제한 | UI를 우회한 타 매장 변경과 잘못된 상태 점프를 막기 위해 | 프론트 버튼 노출만으로 보호 |
| 상태 행을 잠근 뒤 조건부 갱신 | 동시에 두 직원이 처리할 때 오래된 상태를 기준으로 덮어쓰지 않기 위해 | 조회 후 무조건 UPDATE |
| 결제 범위를 `order_master` 방문 단위로 조회 | 현재 DB의 주문/결제 쓰기 범위가 방문 마스터에 묶여 있기 때문에 | 화면의 테이블 번호만 신뢰하거나 클릭한 주문만 결제 |
| 영수증을 POST 전에 서버에서 재조회 | 프론트 캐시의 합계/항목을 권한 또는 결제 진실로 신뢰하지 않기 위해 | 요청 body/footer를 그대로 권위 데이터로 사용 |
| OpenAPI를 실행 중인 새 백엔드에서 재생성 | 기존 8080 프로세스가 이전 `LocalTime` 계약을 노출하고 있었기 때문에 | 생성 타입에 수동 캐스팅 유지 |

DB 스키마는 변경하지 않았다. 기존 테이블/컬럼과 현재 서비스 구조로 먼저 안전 경계를 강화했다.

## 결함과 조치

### D1 주문 완료 번호 병합 누락

- 원인: 완료 응답의 `orderNo` 상태는 있었지만 `OrderCompleteScreen` prop 전달이 병합에서 빠졌다.
- 영향: 주문은 201로 성공해도 사용자가 주문번호를 확인할 수 없었다.
- 조치: `completedOrderNo`를 완료 화면에 전달하고 성공 테스트에서 `0001` 노출을 검증했다.
- 커밋 추적: `feat : (consumer) 주문 완료 번호 표시`

### D2 Client 상태 변경의 서버 경계 부족

- 원인: 주문 그룹 ID만으로 상태를 변경했고 로그인 매장과 기대 상태를 SQL 조건으로 확인하지 않았다.
- 영향: 조작된 요청 또는 동시 요청이 타 매장 주문이나 이미 바뀐 상태를 수정할 가능성이 있었다.
- 조치: 로그인 매장으로 행을 잠그고 허용 전이만 조건부 갱신한다. 주문 상세 변경도 요청 ID 전체의 소유권/변경 가능 상태를 한 번에 확인한다.
- 커밋 추적: `feat : (consumer) 주문 상태와 방문 결제 API 경계 보강`

### D3 결제 영수증 범위 불일치

- 원인: 클릭한 주문 그룹 기준 조회와 방문 마스터 기준 결제 쓰기의 범위가 달랐다.
- 영향: 한 방문에서 추가 주문이 있으면 영수증 항목/합계와 실제 결제 범위가 어긋날 수 있었다.
- 조치: 클릭한 그룹에서 매장 소유 방문 마스터를 구한 뒤, 같은 방문의 미취소 주문 전체를 영수증 본문/합계로 조회한다.
- 커밋 추적: `feat : (consumer) 주문 상태와 방문 결제 API 경계 보강`

### D4 주문 일시 계약 드리프트

- 원인: 백엔드는 `LocalDateTime`인데 기존 실행 프로세스/OpenAPI 생성물은 `LocalTime` 객체 타입을 유지했다.
- 영향: 프론트가 이중 캐스팅으로 계약 오류를 숨겼고 실제 TIMESTAMP 조회 오류와 타입이 어긋났다.
- 조치: DTO에 `date-time` 스키마를 명시하고 새 백엔드 OpenAPI로 생성물을 갱신해 문자열을 그대로 전달한다.
- 커밋 추적: `feat : (consumer) 주문 상태 날짜 계약 동기화`

### D5 미결제 처리의 상태 검증 누락

- 원인: 결제완료만 방문 내 모든 주문의 서빙완료 상태를 검사하고 미결제는 열린 방문 여부만 검사했다.
- 영향: UI를 우회하면 조리 중 주문이 있는 방문도 미결제로 종료할 수 있었다.
- 조치: 결제완료/미결제 모두 같은 행 잠금과 서빙완료 검증을 거치게 하고 회귀 테스트를 추가했다.
- 커밋 추적: `feat : (consumer) 주문 상태와 방문 결제 API 경계 보강`

## 자동 검증 근거

2026-09-14 현재 작업 트리 기준 결과다. 작업은 2026-09-08에 시작했으나 최종 재검증은 재개일에 수행했으므로 R13의 원래 완료일은 충족했다고 표시하지 않는다.

| 검사 | 결과 |

| Consumer 대상 프론트 테스트 | 6 files / 46 tests 통과 |
| 프론트 전체 테스트 | 123 files / 541 tests 통과 |
| 프론트 TypeScript 검사 | 통과 |
| 프론트 ESLint | 통과 |
| 프론트 production build | 통과 / chunk size 경고만 존재 |

테스트가 증명하는 핵심 경계는 타 매장 상태 변경 거부, 예상 밖 상태 전이 거부, 섞인 주문 상세 ID의 원자적 거부, 방문 전체 영수증 조회, 서빙 전 결제완료/미결제 거부, Consumer 주문번호 표시다.

## `dev:real` 수동 QA 절차

전제: 현재 브랜치 백엔드를 8080에서 재시작하고 실제 Client 계정/매장 데이터/QR URL을 사용한다. 기존 8080 프로세스가 예전 빌드면 이번 수정 검증이 아니다.

1. `frontend`에서 `npm run dev:real`을 실행한다.
2. Client 로그인 후 실제 QR 관리 화면에서 테스트 테이블의 QR URL을 얻는다.
3. QR로 Consumer에 진입해 세션/메뉴 메인/검색/상세 요청이 성공하는지 확인한다.
4. 옵션/수량이 있는 주문을 생성하고 POST 201, 완료 화면 주문번호, 장바구니 제거를 확인한다.
5. Consumer 주문 목록/상세와 Client 주문현황의 메뉴/옵션/수량/금액을 대조한다.
6. 같은 방문에서 주문을 하나 더 생성하고 두 주문을 접수/조리중/서빙완료로 이동한다.
7. 결제 영수증에 두 주문과 방문 합계가 포함되는지 확인하고 결제완료 후 Client 카드가 사라지는지 확인한다.
8. Consumer를 새로고침해 세션 CLOSED 처리와 장바구니 제거를 확인한다.
9. 테이블을 비활성화한 뒤 기존 주문 조회는 유지되고 새 POST만 `409/TABLE_INACTIVE`인지 확인한다. 장바구니/요청 ID가 유지되어야 한다.
10. 다시 활성화해 재시도하고 Network 탭에서 같은 `clientRequestId`가 전송되는지 확인한다.
11. 브라우저 Offline 또는 요청 지연으로 실패시킨 뒤 장바구니/요청 ID 유지와 재시도를 확인한다.

각 항목은 요청 URL/상태 코드/응답과 화면 캡처를 함께 남긴다. 이 절차를 실행하기 전에는 실제 연동 QA 완료로 판정하지 않는다.

## 남은 한계 / 후속 작업

- 서버 영속 멱등성은 요청/응답 저장 테이블이 없어 아직 보장되지 않는다. 현재 `clientRequestId` 보존은 클라이언트 재시도 식별까지만 담당한다.
- Client 역할별 상태 변경 권한 정책은 확정된 계약이 없다. 이번 변경은 기존 로그인 사용자 정책을 유지하고 매장 경계만 강화했다.
- 실제 DB를 사용한 동시 상태 변경/다중 주문 결제 경쟁 테스트는 수동 또는 통합 테스트가 필요하다.
- 심층 리뷰 에이전트는 2026-09-14 외부 사용량 제한으로 3건 모두 실행 실패했다. SQL/서비스/테스트 직접 리뷰에서 미결제의 서빙완료 검증 누락을 찾아 수정했지만, 독립 리뷰 결과는 없는 상태다.
- 주문 수정 저장, `requestNote` 컬럼, QR PIN, Consumer SSE/참여 인원은 이번 범위가 아니다.
- `origin` push는 수행하지 않는다.
