# Consumer 001/002/003 핵심 수동 QA

> 대상: visit-payment-flow / consumer-sse-integration / ttl-request-note
> 기준 환경: 병합된 `dev` / 실제 백엔드 / `npm run dev:real`
> 범위: 결제/미결제, Consumer SSE, 메모리 기반 10분 주문 멱등성

`ttl-request-note` 브랜치에서 이번 QA 대상은 구현된 TTL 멱등성이다. 메뉴별 `requestNote`는 TODO라서 이 문서에서 검증하지 않는다.

## 준비

- 백엔드와 프런트를 실행하고 Client 직원 계정으로 로그인한다.
- 같은 QR을 Consumer A/B 브라우저에서 연다. 가능하면 서로 다른 브라우저나 시크릿 창을 쓴다.
- 개발자 도구 Network에서 Preserve log를 켜고 `events`, `orders`, `session` 요청을 확인한다.
- 테스트마다 주문번호, `clientRequestId`, HTTP 상태, 실제 결과를 기록한다.
- 결제/미결제로 방문을 닫으면 되돌릴 수 없으므로 종료 시나리오마다 새 방문을 사용한다.

## P0 / 반드시 통과

### QA-1 / 주문 생성, SSE 공유 갱신

1. A/B에서 같은 방문의 `/api/client/consumer/events`가 Pending인지 확인한다.
2. A에서 메뉴를 주문한다.
3. A의 POST `/api/client/consumer/orders`가 `201`인지 확인한다.
4. B에서 새로고침하지 않고 주문내역을 연다.

기대 결과:

- A/B stream에 `ORDER_CREATED`가 수신된다.
- B 주문내역에 같은 주문번호/메뉴/옵션/수량/금액이 표시된다.
- B가 다른 방문이면 해당 주문이 보이지 않는다.

결과: [o] 통과 / [ ] 실패

### QA-2 / 동일 주문 요청 재전송

1. QA-1의 주문 POST를 Network에서 선택해 Payload의 `clientRequestId`를 기록한다.
2. Copy as fetch로 복사해 Console에서 내용 변경 없이 한 번 더 실행한다.
3. 응답과 Client 주문현황을 확인한다.

기대 결과:

- 재전송도 `201`이며 최초 응답과 `orderId`, `orderNo`, 금액이 같다.
- Client 주문 수와 DB 주문 수가 증가하지 않는다.

결과: [o] 통과 / [ ] 실패

### QA-3 / 같은 키에 다른 주문 내용 거부

1. QA-2의 fetch에서 `clientRequestId`는 유지하고 메뉴 수량 하나만 바꾼다.
2. Console에서 요청하고 주문 목록을 다시 확인한다.

기대 결과:

- 서버가 `409`와 멱등성 충돌 오류를 반환한다.
- 신규 주문이 생기지 않는다.
- UI 경로에서 충돌할 경우 장바구니와 요청 식별자가 유지된다.

### QA-4 / 주문 상태와 결제 완료 실시간 반영

1. Client 앱에서 QA-1 주문을 접수 / 조리 / 서빙 완료 순서로 변경한다.
2. 각 단계마다 A/B의 주문내역을 새로고침하지 않고 확인한다.
3. 서빙 완료 후 결제 완료 처리하고 A/B의 방문 종료를 확인한다.

기대 결과:

- Consumer stream에 단계마다 `STATUS_CHANGED`가 수신된다.
- A/B의 주문 상태가 기존 주문 조회 API 결과로 갱신된다.
- 메뉴/옵션/수량/금액은 바뀌지 않는다.
- 결제 완료가 성공하고 `VISIT_CLOSED` 수신 후 A/B가 `CLOSED`로 전환된다.

결과: [ ] 통과 / [X] 실패

실패 현상 :

- 결제 실패

- "error": "409 CONFLICT \"모든 주문의 서빙이 완료된 후 결제할 수 있습니다.\"",

### QA-5 / 서빙 전 결제 완료 차단

1. 새 방문에서 주문을 생성하고 접수 또는 조리 상태로 둔다.
2. Client 앱에서 결제 완료를 시도한다.

기대 결과:

- 요청이 `409`로 거부되고 완료 안내가 표시되지 않는다.
- Client 상태와 Consumer 주문/세션은 종료 전 상태를 유지한다.
- `VISIT_CLOSED`가 수신되지 않는다.

결과: [ ] 통과 / [ ] 실패

### QA-6 / 서빙 전 미결제 방문 종료

1. QA-5 방문을 접수 또는 조리 상태로 유지한다.
2. 미결제 사유 `CUSTOMER_ABSENT`로 미결제 처리한다.
3. A/B에서 종료 결과를 확인하고 추가 주문을 시도한다.

기대 결과:

- 미결제 처리가 성공하고 Client 주문현황에서 열린 방문이 제거된다.
- Consumer stream에 `VISIT_CLOSED`가 수신되고 A/B가 `CLOSED`로 전환된다.
- 기존 주문 조회 결과는 유지되지만 새 주문은 거부된다.
- 결제현황에는 미결제로 일관되게 표시된다.

## P1 / 장애 복구 확인

### QA-7 / SSE 단절 중 polling과 재연결

1. 활성 방문에서 개발자 도구 Request blocking으로 `*/api/client/consumer/events*`를 차단한다.
2. 10초 이상 기다려 세션/주문 GET이 약 5초 간격으로 발생하는지 확인한다.
3. Client에서 주문 상태를 변경해 Consumer 화면이 polling으로 갱신되는지 확인한다.
4. 차단을 해제하고 SSE가 다시 Pending 상태가 되는지 확인한다.

기대 결과:

- 연결 실패 중에도 기존 화면과 장바구니가 유지된다.
- polling으로 상태가 갱신된다.
- 재연결 후 반복 polling이 멈추고 SSE 연결이 하나만 유지된다.
